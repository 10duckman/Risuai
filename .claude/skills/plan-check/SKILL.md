# Plan Check — 실행 전 체크포인트

작업을 시작하기 전에 아래 체크리스트를 순서대로 확인합니다. 각 항목을 ✅/❌로 체크하고, ❌가 있으면 해결 방안을 먼저 제시합니다.

---

## Phase 1: 현상 파악 (Analyze First)

### 1-1. 동작하는 사례를 먼저 봤는가?
- 비슷한 기능이 이미 동작하는 곳이 있는가? (다른 파일, 다른 프로젝트, 참조 코드)
- 그 코드의 **실제 데이터/구조**를 직접 확인했는가? (추정이 아닌 실측)
- 예: customscript를 만들기 전에 한유진 카드의 customscript를 먼저 추출/분석

### 1-2. 문제의 범위가 명확한가?
- 무엇이 안 되는지 한 문장으로 설명할 수 있는가?
- 원인 가설이 있는가? 가설이 여러 개면 어떤 순서로 검증할 것인가?
- 예: "SSE가 끊기면 recovery가 안 됨" → 원인: 서버 크래시? 클라이언트 감지 실패? 배포 안 됨?

## Phase 2: 계획 (Plan Before Code)

### 2-1. 변경 파일과 함수가 명확한가?
- 어떤 파일의 어떤 부분을 수정할 것인지 목록화
- 변경이 다른 코드 경로에 영향을 주는지 확인 (예: 게이트웨이 모드만 vs 전체 스트리밍)

### 2-2. 검증 방법이 있는가?
- 수정 후 어떻게 확인할 것인가? (빌드 확인, grep, 실제 테스트)
- 자동 검증이 가능한가? (스크립트로 확인할 수 있는가)
- 예: `grep -c "stream_complete" dist/assets/index-*.js` → 0이면 빌드 실패

### 2-3. 롤백이 가능한가?
- git commit 되어있는가?
- DB 수정이면 백업을 먼저 만드는가?
- 배포면 이전 이미지로 롤백할 수 있는가?

## Phase 3: 실행 전 최종 확인

### 3-1. 한 번에 하나만 바꾸고 있는가?
- 여러 문제를 동시에 고치면 어떤 수정이 효과가 있었는지 모른다
- 하나 고치고 → 검증 → 다음 하나

### 3-2. 빌드/배포 파이프라인이 신뢰할 수 있는가?
- Docker 캐시 문제는 없는가? (`--no-cache` 필요?)
- 새 코드가 실제로 빌드 결과물에 포함되었는지 확인하는 단계가 있는가?

### 3-3. 유저에게 설명할 수 있는가?
- 지금 하려는 변경을 한 문장으로 설명할 수 있는가?
- 왜 이 방법이 맞는지 근거가 있는가? (추정 vs 실측)

## 출력 형식

```
## Plan Check 결과

| # | 항목 | 상태 | 비고 |
|---|------|------|------|
| 1-1 | 동작 사례 분석 | ✅/❌ | ... |
| 1-2 | 문제 범위 | ✅/❌ | ... |
| 2-1 | 변경 목록 | ✅/❌ | ... |
| 2-2 | 검증 방법 | ✅/❌ | ... |
| 2-3 | 롤백 가능 | ✅/❌ | ... |
| 3-1 | 하나씩 변경 | ✅/❌ | ... |
| 3-2 | 빌드 신뢰성 | ✅/❌ | ... |
| 3-3 | 설명 가능 | ✅/❌ | ... |

**판정**: 진행 가능 / ❌ 해결 필요
```

❌가 하나라도 있으면 해결 방안을 먼저 제시하고, 유저 확인 후 진행합니다.
