# 대화 → 로어북 추출 설계

작성일: 2026-08-01
대상: RisuAI 포크

## 배경

긴 대화가 컨텍스트를 잡아먹는다. 웬디스 대화는 209턴, assistant 686,344자이고
매 요청 입력이 60만 토큰이다. 생성에 4~5분 걸리고, 가장 오래된 메시지는 이미
컨텍스트에서 밀려났다 (`messages[0]`이 5자로 잘렸다).

기존 대응은 HypaMemory V3다. 알고리즘이 오래된 대화를 요약해 벡터 검색으로
불러온다. 문제는 **무엇이 중요한지를 알고리즘이 정한다**는 점이다. 요약이
빗나가도 사용자가 개입할 수단이 없고, 결과물은 바이너리 JSON 안에 있어 읽거나
고칠 수 없다.

로어북은 다르다. 사람이 읽고 편집 가능한 텍스트이고, 항목 단위로 껐다 켤 수
있고, 틀렸으면 직접 고친다. 이 기능은 대화를 로어북 항목으로 추출해 사용자가
취사선택하게 한다. 추출된 구간은 채팅에서 지워도 필요할 때 되살아난다.

## 무엇이 이 기능의 성패를 가르는가

**요약은 로어북 항목이 아니다.**

```
요약:        "만세는 무심한 남편이다"
             → 모델이 읽고 넘어간다

micro-detail: "41세. 자칭 화가. 17년 무직."
             "술 취하면: '네가 없으면 난 아무것도 아니야'"
             "전희 없음. 불 끄고. 체위 하나. 평균 4분."
             → 모델이 본 적 없는 장면에서 그 인물을 즉흥 연기한다
```

전자를 만들면 이 기능은 HypaMemory와 다를 게 없어 존재 이유가 없다.

결과가 설계의 기준이다. 상세는 `.superpowers/sdd/lorebook-export/songhari-structure.md`.

| 항목 | 크기 | mode | alwaysActive | key |
|---|---|---|---|---|

대신 CBS 조건 분기(`{{#if {{? ($lust>0)&($lust<21)}}}}`)로 활성 영역을 좁힌다 —
Status는 18,676자를 보유하지만 40개 단계 중 축당 하나씩 4개만 조건을 만족하므로
실제 주입은 그 1/10이다.

인물 하나는 2,848자에 고정 9라벨이다. 그 라인들의 성질:

- **직접 인용** — `Drunk: "I'd be nothing without you."`
- **구체 행동** — 매일 문에서 맞이하고 앞치마를 받는다
- **부재의 명시** — `Missionary only. Lights off. No foreplay.`

평가 술어가 한 줄도 없다. 전부 관찰 가능한 사실이다.

### Status는 추출 대상이 아니다

4축 × 10단계는 카드 제작자가 손으로 설계한 게임 메커니즘이다. 대화 기록에서
자동 추출할 성질이 아니다. 이 기능은 Family/World 형태를 목표로 한다.

## 설계

프롬프트 전문과 스키마는 `.superpowers/sdd/lorebook-export/final-prompts.md`에
있다. 여기서는 구조와 결정만 다룬다.

### 1. 처리 흐름

```
사용자가 채팅 메뉴에서 "로어북으로 추출" 선택
  → 범위 선택 (전체 / 최근 N턴 / 구간 지정)
  → 20~30턴 단위로 분할 (웬디스 209턴이면 약 11청크)
  → 청크별 추출 (Opus 5, 병렬 아님 — 순차)
  → 코드 검증 5단계로 fact 걸러내기
  → merge (Opus 5, 1회) — 인물/장소/상태 통합, 사물 누적
  → 미리보기: 항목별로 캐릭터 로어북 / 채팅 로어북 / 버리기 선택
  → 확정한 것만 globalLore 또는 localLore에 추가
```

### 2. 추출 단위: fact

각 fact는 여섯 형태 중 하나다.

| 타입 | 뜻 | 예 |
|---|---|---|
| `num` | 숫자를 포함 | "17년 무직", "맥주 1-2캔" |
| `quote` | 대사를 그대로 | "네가 없으면 난 아무것도 아니야" |
| `trigger` | 조건 + 반응/발화 | "술 취하면: '네가 없으면...'" |
| `habit` | 반복 관측된 행동 | "매일 문에서 맞이하고 앞치마를 받는다" |
| `absence` | 하지 않는 것 | "전희 없음", "5개월간 방에서 안 나옴" |
| `plain` | 짧은 명사구 | "송진 냄새를 싫어한다", "HG 에어리얼" |

각 fact에 `src`를 단다 — 근거가 되는 원문 조각을 5~60자 그대로 옮긴다.

**`trigger`가 이 설계의 핵심 추가다.** 실물에서 가장 생성력 높은 13개 라인이
조건+발화 쌍이고(`"Serious talk" request met with sigh: "money thing again?"`),
이것만이 모델에게 if-then을 준다. 검토한 세 접근 모두 이 슬롯이 없었다.

### 3. 슬롯 라벨 9개

```
Identity    나이 성별 직업 소속
Appearance  키 몸무게 특징
History     과거 사건, 만난 경위
Habits      반복하는 행동
Speech      말투와 실제 대사 (quote 2개 이상)
Reactions   어떤 상황에서 어떻게 반응하는가 (trigger 위주)
Relations   다른 인물에 대한 태도
Absences    하지 않는 것
Misc        나머지
```

실물의 9라벨을 그대로 쓰지 않았다. 실물 `Personality` 조각의 41%가 평가어이기
때문이다 (`Good person.` `Genuinely believes he is a genius.`) — 그것이 그 문서의
`만세는 무심하다`다. 실물을 복사하면 결함까지 복사한다. `Personality`를 제거하고
`Habits` / `Speech` / `Reactions`로 쪼갰다.

장소는 `Place`, 관계 상태는 `State`, 사물·모티프는 `Object`로 같은 방식.

### 4. 인물 통과 조건

```
(trigger + quote) >= 3  &&  fact 총합 >= 8  &&  분포된 슬롯 >= 3
```

못 넘으면 **그 인물을 버린다. 재요청하지 않는다.** 재요청은 쿼터를 채우려는
날조를 유발한다.

비율 쿼터는 쓰지 않는다. 검토 과정에서 "숫자 또는 인용 40% 이상"이 제안됐으나
실측 반박이 결정적이었다 — 실물 6명 중 4명이 그 쿼터를 통과하지 못한다
(Manse v1 38%, Heeyul 16%, Heeyeon 23%, Seowoo 12%). 게다가 비율은 재시도에서
분모를 줄이는 쪽으로 최적화된다.

필수 `absence`·필수 비교(`cmp`)도 쓰지 않는다. 25턴 청크에서 관측 불가능한 것을
요구하면 날조한다. 실물의 `딸 신발 사이즈를 하리보다 먼저 안다`는 22KB 수제
문서의 한 줄이다.

### 5. 코드 검증 5단계

프롬프트만으로는 부족하다. 청크 결과를 받은 뒤 코드가 검사한다.

**(1) src verbatim** — `fact.src`가 청크 원문에 그대로 있는가. 없으면 버린다.
`absence`는 제외 (부재는 원문에 진술되지 않는다).

**(2) src → v 연결** — 이것이 가장 중요하다. 앵커가 원문에 있다는 것만으로는
부족하다. `src:"대답도 없이 방으로"` + `v:"무심하다"`가 통과해버린다.

```
num     → src의 숫자열이 v에도 나타나야 한다
quote   → src 전문이 v의 " " 안에 글자 그대로
trigger → v에 조건부와 반응부가 모두 (구분자 ':' 또는 '→')
```

**(3) 평가어 denylist** — `v`가 아래 정규식에 매치되면 버린다.

```
/무심|다정|순수|차갑|따뜻|냉정|헌신적|성실|가정적|착하|나쁘|훌륭|
 (적|스러운|로운)이다|한 편이다|경향이 있다|편이다|같다|보인다/
```

**(4) 인물 통과 조건** — 위 4절의 조건. 못 넘으면 merge에 넘기지 않는다.

**(5) always-on 총량** — merge 결과에서 `alwaysActive: true` 항목의 `content`
합이 5,000자를 넘으면 경고하고 사용자에게 어느 항목을 키워드로 내릴지 묻는다.

현재 프롬프트가 39,588자이고 그중 모듈 로어북이 12,258자다. 여기에 5,000자가
더해진다.

### 6. merge 규칙

**인물 / 장소** — 같은 대상의 fact를 모은다. 중복 제거, 같은 사실의 다른 표현은
더 구체적인 쪽. 모순되면 **둘 다 남기고 시점을 붙인다** — 관계는 변하고 변화
자체가 정보다 ("처음에는 존댓말. 100턴 이후 반말."). 별칭은 같은 인물로 묶고
`key`에 모두 넣는다.

**관계 상태** — 최신만. 과거는 History로.

**사물·모티프** — 누적. 등장 시점과 그때의 의미를 함께.

**`absence` 승격** — 청크의 `absence`는 "이 구간에 없었다"는 뜻일 뿐이다.
여러 구간에서 일관되게 없으면 사실로 승격, 한 구간에만 없거나 다른 구간에서
반증되면 버린다.

### 7. 카드 설정과 겹칠 때

**대화가 이긴다.** 카드에 있는 내용이라도 대화가 더 구체적으로 만들었으면
대화 쪽을 쓴다 (`직장인` → `마케팅팀 대리 3년차`). 글자까지 같은 것만 제외한다.

### 8. 활성화 방식

| 항목 | alwaysActive | key | insertorder |
|---|---|---|---|
| 인물 | true | "" | 100 |
| 장소 | true | "" | 90 |
| 관계 상태 | true | "" | 110 |
| 사물·모티프 | false | 이름·별칭 쉼표 나열 | 50 |

인물·장소·상태는 매 턴 필요하므로 always-on이다. 사물은 언급될 때만 필요하므로
키워드다. 흔한 단어(집, 밤, 손)는 `key`에 넣지 않는다 — 매 턴 발동한다.

실물 로어북이 키워드를 아예 쓰지 않는 것과 다른 선택이다. 실물이 always-on으로
갈 수 있는 이유는 Status가 CBS로 자체 필터링하기 때문인데, 추출 항목에는 그
메커니즘이 없다. 사물까지 always-on으로 두면 컨텍스트를 계속 먹는다.

### 9. 모델

청크 추출과 merge 모두 **메인 모델(Opus 5)**. UI에서 바꿀 수 있게 두되 기본값은
메인이다.

처음에는 청크를 submodel로 돌릴 계획이었으나 실제 설정을 확인하니 `subModel`이
`claude-opus-4-7`이었다 — 코드 기본값(`gemini-3-flash-preview`)이 아니다. 이름과
달리 이미 메인급이므로 나눌 이유가 없고 `src` verbatim 준수를 걱정할 필요도 없다.

비용은 청크 11회로 적지 않다. 다만 한 번 추출하면 계속 쓰는 자산이고, 추출한
구간을 대화에서 지워 매 턴 60만 토큰을 줄이는 것이 목적이므로 회수된다.

### 10. UI

**진입점** — `alertChatOptions()` (`src/ts/alert.ts:110`). 채팅 목록에서 여는
"채팅 옵션" 메뉴로, 현재 `createCopy` / `bindPersona` / (experimental 항목) 이
들어 있다. 여기에 "로어북으로 추출"을 추가한다.

이 자리를 고른 이유: 메시지 단위가 아니라 **채팅 단위** 작업이다. 앞서 만든
"서버에서 동기화"는 특정 메시지를 지목하므로 `minorIconButtonsBody`가 맞았지만,
추출은 대화 전체 또는 구간을 대상으로 한다.

메뉴는 `alertStore`의 `msg`에 인덱스 문자열을 넣고 `parseInt`로 반환하는 구조다
(`AlertComp.svelte:663~`). 항목 추가는 버튼 하나와 인덱스 분기 하나다.

**미리보기** — 추출 결과를 항목별로 보여주고 각각에 대해:
- 캐릭터 로어북(`globalLore`)에 추가
- 채팅 로어북(`localLore`)에 추가
- 버리기

merge가 `dropped` 배열로 "무엇이 왜 버려졌는지" 함께 반환한다. 사용자가 판단할
근거가 있어야 한다.

**편집** — 추가된 항목은 기존 로어북 UI(`src/lib/SideBars/LoreBook/`)에서
그대로 편집된다. 별도 편집기를 만들지 않는다.

## 범위 밖

- **Status(4축 10단계) 생성** — 손으로 설계하는 게임 메커니즘이다.
- **CBS 조건 분기 생성** — 변수 체계를 자동으로 설계하는 것은 다른 문제다.
- **채팅에서 구간 삭제** — 추출 후 대화를 줄이는 것은 사용자가 기존 기능으로
  한다. 이 기능은 추출까지만 한다.
- **HypaMemory 대체** — 병행 가능하다. 이 기능이 HypaMemory를 끄게 만들지는
  사용자가 판단한다.
- **로어북 항목 비활성화 토글** — `loreBook` 타입에 `disabled` 플래그가 없다.
  껐다 켜기가 실제로 가능한지는 별도 확인이 필요하다.

## 검증 기준

1. 웬디스 대화(209턴)에서 추출하면 인물 항목이 생성된다
2. 생성된 인물 항목에 평가어(`무심하다` 류)가 0개다
3. 각 인물 항목에 `trigger` 또는 `quote`가 3개 이상 포함된다
4. `src`가 원문에 없는 fact는 결과에 나타나지 않는다
5. `src:"..."` + `v:"무심하다"` 조합이 검증 2단계에서 걸러진다
6. 통과 조건 미달 인물은 결과에 나타나지 않는다
7. always-on 항목 합이 5,000자를 넘으면 경고가 뜬다
8. 미리보기에서 항목별로 캐릭터/채팅/버리기를 고를 수 있다
9. `dropped`에 버려진 이유가 표시된다
10. 확정한 항목이 `globalLore` 또는 `localLore`에 정확히 들어간다
11. 추가된 항목이 기존 로어북 UI에서 편집된다
12. 인물 항목이 2,000~3,000자, 장소가 1,000~2,000자 범위다

## 남은 판단

**`absence` 승격의 정확도** — merge가 "여러 구간에서 일관되게 없음"을 판정하려면
각 구간이 그 대상을 다뤘는지 알아야 한다. 지금 스키마로는 "언급 안 됨"과 "없다고
관측됨"을 구별하기 어렵다. 첫 실행 결과를 보고 보강한다.

**키워드 항목의 실효성** — 실물 로어북은 키워드를 쓰지 않는다. 키워드 매칭이
실제로 유용한지는 이 기능이 처음 검증하는 셈이다.
